## 文本请求与安全恢复

- 同一文本 HTTP 入口和凭据共享排队容量，默认并发 2、最长排队 5 分钟。
  多进程使用同一个独立小型 SQLite，避开大型生产数据库的写锁。
- 明确 HTTP 429 共享冷却时间，保留 Retry-After。排队超时会标明请求尚未发送。
  此协调器不重放已经发出的请求；API 密钥、提示词和响应不写入协调数据库。
- 仅最新、24 小时以内、明确被限流拒绝的 YouTube 采集允许自动继续。
  等待至少 30 / 60 / 120 秒，同时遵守供应商更长的等待要求；最多自动恢复 3 次，预算跨重启保留。
- 停止、新采集、缺少执行器及未知错误都会阻止自动恢复。恢复沿用原任务及检查点。
- 生产进展观察排除心跳时间变化，按真实状态、阶段和进度消息计时。
  停滞仅显示提醒，不因等待太久而取消、重建付费远端项目。
- 发表审核检查保留每分钟最多 2 次、上传优先和持久退避，每轮兼顾一个新提交作品和最久等待作品。

配置见 `backend/.env.example` 的 `AI_TEXT_*`。共享排队覆盖 `callTextModel` 文本入口；
直接 SDK、其他 HTTP 入口、图片和音频服务不在此次容量协调范围内。

## 独立磁盘维护

主后端移除重复定时清理。独立维护服务负责启动扫描、到期补一次清理、失败重试和健康状态。
沿用原 `autoCleanup=true, retentionDays=0` 策略；实际删除仍要求对应版本的有效发表证据、
内容身份、无活动消费者、无 pin，且在最终写事务中再次核验。待审核提交、未知上传结果、
工程输入和原有保护条件继续阻止删除。

同一清理中的多副本复用完全相同 JSON 的解析结果；大参数绑定在写锁前完成，
锁内继续核对实时值、行身份、数量和表结构。路径索引减少宽表扫描，保留原路径匹配语义。

## 素材增量更新

已实现默认增量更新，覆盖实际素材更新任务调用的收集器：

- 每次仍检查远端项目和分镜列表，以发现新增项目、分镜和变化；不把本地更新时间当作新鲜度证据。
- 远端身份、文本、检索和媒体字段、可用版本信息及完整推荐快照一致的分镜，跳过推荐请求和完整推荐表重写。
- 新增、变化、失败或不完整的分镜定向读取；本地逐文件核验类型、大小和完整 SHA-256，缺失或损坏才补齐。
- 跨项目同一素材共用在途下载，并用核验后的硬链接复用；隔离双项目样例由 6 次传输降至 3 次。
- 损坏文件仅在新文件完成校验后原子替换；保留未知文件、符号链接、竞争写保护及原有磁盘余量检查。
- 缓存下载地址返回 401/403/404/410 时，仅刷新所属分镜一次；分镜顺序变化不会导致重新下载已有有效素材。
- 进度及任务结果增加读取分镜、跳过分镜和补齐文件数量，旧结果兼容为 0。

旧缓存第一次需要补建完整校验记录，已有有效视频仍复用。若远端只改变推荐结果却不暴露分镜变化，
可用收集器 CLI 的 `--refresh-metadata` 强制刷新。实现与 102 项回归证据见 `material-incremental-result.md`。

已在旧主进程执行的素材更新 #40333 正常完成：134 个项目、8,952 个分镜、
新增 3,329 个视频、复用 23,400 个视频，失败 0；该次执行不能作为新增量逻辑的线上验收。
