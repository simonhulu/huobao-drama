# 历史批量视频的渲染方案选择

核查日期：2026-11-01。目标环境是本机 M1 Mac、16 GB 内存，产出是视频素材、图片运动、字幕、解释图层、地图和配音组成的长视频，并要求批量自动生产、硬件编码、任务可恢复和上传确认后的定向清理。

## 结论

优先改进素材匹配、片内选段、镜头设计和生图调度；FFmpeg 与 Remotion 分工保留为待验证的性能方案。上一版把渲染器改造放在首位，没有证明收益幅度，也没有给出足够的质量提升机制，不能据此作为完整升级方案。

video-shotcraft 的价值应放在复用经过设计的镜头表达上。HyperFrames 虽然同样使用浏览器，但截帧、静态去重、流式输出和缓存实现不同，不能因为底层都使用 Chrome 就断定性能相同。剪映草稿适合人工精修；当前两个自动化项目的 Windows 导出依赖仍然成立。

这是结合源码和现有制作结构的架构建议，没有完成 FFmpeg 分流实现，也没有做这些工具之间的同负载速度或画质对比。2026-11-02 已追加镜头语法、四类伴随图解、两路补图队列和候选证据优先选择，实际代码与样片见[实施记录](plans/2026-11-01-history-shotcraft-optimization.md)。

## 修订后的升级优先级

1. **先改善画面与旁白的对应。** 在素材进入库时建立可复用的片段视觉索引，记录可见动作、时代线索、景别、字幕和可用时间范围。制作时按叙事需要选片、选段，复用观察结果，降低反复在线抽检与预算耗尽的影响。
2. **建立少量历史叙事镜头模板。** 借鉴 video-shotcraft 的构图、缓动和声音设计，形成地理定位、人物抉择、关系变化、时间推进、攻守变化等表达。按内容选择镜头并保持人物与视觉风格连续，不机械给全部图片加同一种缩放。
3. **缩短完整制作周期。** 生图按服务限额并行提交和轮询，完成镜头持久化；失败只重做对应镜头。明确记录生图、排队、绘制和封装，避免只优化最后几分钟。
4. **用真实片段决定渲染路线。** 先选同一稿件的一小段作为质量验收样片，比较画面是否更准确、重点是否更清楚、运动是否有目的以及完整耗时；据此决定采用 Remotion、HyperFrames 的特定优化，或 FFmpeg 分流。现有资料不足以宣布任何替代引擎同时更快且更好。

上述第 2 项的图片运动及伴随图解、第 3 项的有界并行补图已实现；选材现会在最多三个候选中优先使用已抽检可用的素材。全库视觉索引、片内动作定位和替代引擎分流尚未实现，不能把本轮局部优化视为这些工作的完成。

## 候选比较

| 方案 | 实际承担的工作 | 对本机批量生产的意义 |
| --- | --- | --- |
| video-shotcraft | 镜头配方、模板、动效和制作流程，仍使用 Remotion | 可改善镜头表现；不是替代渲染器，无法自行消除整片浏览器渲染成本 |
| CapCut Mate | 生成剪映草稿，并通过 Windows 剪映界面自动导出 | 适合有 Windows 工作站和原生剪映编辑需求的流程；不能直接替换 Mac 无人值守 MP4 渲染 |
| jianying-editor-skill | AI 驱动草稿编辑，macOS 导出转交 Windows Agent | 强项是可编辑工程和人工精修；完整自动导出仍依赖 Windows GUI 和剪映版本 |
| HyperFrames | HTML/动画时间线、Chrome 截图、FFmpeg 编码 | 可流式编码以减少中间帧 I/O，也支持 VideoToolbox；仍有浏览器逐帧成本，默认/降级策略还需适配严格硬编要求 |
| FFmpeg 为主，Remotion 处理复杂镜头 | 素材直接解码、剪辑、合成和硬编，复杂镜头单独生成 | 优先减少当前不必要的网页布局、截图和数据搬运；适合已有素材占多数的长视频，需实现视觉等效并验证实际收益 |

video-shotcraft 的官方实现和剪映导出说明见[固定版本](https://github.com/Vincentwei1021/video-shotcraft/tree/1266a3ec4831289c4d893d42dd5102723658039a)。剪映项目的 Windows、GUI、串行导出及版本要求，见[逐项源码证据](render-alternatives-capcut-research-20261101.md)。HyperFrames 的流式编码、硬件开关及回退行为，见[逐项源码证据](render-alternatives-hyperframes-research-20261101.md)。

## 为什么普通镜头不需要浏览器

现有入口 `backend/src/services/history-motion-pipeline.ts` 每次启动 `scripts/history-motion/render.mjs`，后者把整片交给 `remotion/src/HistoryMotionFactory.tsx`。普通视频、图片、全局字幕和复杂地图共用 React 合成，所以普通素材也必须通过 Chrome 输出画面。这是实现上的统一方式，不是剪辑视频的必要条件。

FFmpeg 同样会逐帧处理需要改动画面的视频；省下的是网页布局、截图和跨进程输送的额外工作，并不是消除视频帧本身。它已有 [subtitles/libass](https://ffmpeg.org/ffmpeg-filters.html#subtitles)、[zoompan](https://ffmpeg.org/ffmpeg-filters.html#zoompan)、[overlay](https://ffmpeg.org/ffmpeg-filters.html#overlay)、[xfade](https://ffmpeg.org/ffmpeg-filters.html#xfade) 和 [concat](https://ffmpeg.org/ffmpeg-filters.html#concat) 等成熟能力。对应[核查版本源码](https://github.com/FFmpeg/FFmpeg/blob/e2740a3e0daab338b0ec60de407e444f68f9d119/doc/filters.texi#L23888)。

H.264 编码使用 VideoToolbox 不代表字幕、滤镜和布局全部运行在 GPU 上。字幕样式、转场和裁剪仍需逐项匹配。只有参数兼容且不必修改像素的片段，才有条件直接拷贝压缩码流；带烧录字幕的成片通常还需编码。

## 候选性能改造的实现边界

1. 保留同一份制作计划作为时间、素材、字幕、图层和音轨的依据，不重写素材搜集、生图、配音或上传系统。
2. 明确普通镜头支持的行为，包括裁剪、变速、末帧延长、图片平移缩放、字幕、标题和转场。不能因换渲染器丢失现有效果。
3. 能以 FFmpeg 或一次性静态图层实现的镜头直接进入合成；需要复杂动态地图、关系图或网页布局的镜头才调用 Remotion，并缓存其结果。
4. 优先采用流式处理并减少重复编码。必须物化的中间片段关联任务、镜头和输入指纹，按实际占用限制并发；不要为了加速复制整套素材。
5. 沿用现有上传回执和磁盘生命周期规则：运行中输入及唯一产物受到保护，只有满足既定保留条件的缓存才能清理，最终文件必须满足上传确认条件才可删除。
6. 验收检查同一计划的镜头边界、字幕文本和位置、解释图层、地图、转场、音画同步、真实编码器和上传体积。速度判断采用真实阶段数据，不把排队、生图、绘制和编码混为一谈。

## 质量判断

素材选择、历史准确性、镜头安排和字幕可读性决定内容与视觉设计质量。编码器、码率、缩放和重复压缩决定保真度。替换编辑框架不会自动提高这两类质量。video-shotcraft 主要帮助镜头设计；剪映便于人工精修；FFmpeg 路径的目标是在保留画面的前提下减少处理成本。
