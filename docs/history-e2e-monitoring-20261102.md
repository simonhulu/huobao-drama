## 本轮发现并修复的问题

1. **二创引文不精确、429 被误算为坏素材。** 对完整结构中的无效引文做一次限定修复，只允许修复原无效字段并重新验证原文匹配；明确拒绝的 429 有限退避。采集器遇到全局限流暂停原批次并保留检查点，避免继续下载替代来源。
2. **花生浏览器准备暂时失败。** 仅在创建项目之前、尚无外部项目和未知创建检查点时重试一次；176/179 已沿用原任务恢复，未重复创建。
3. **磁盘不足被泛化成进程退出错误。** 保留 `MEDIA_DISK_FULL` 原因和可恢复材料。900 曾触发 10 GiB 保护，之后用同一 Episode 的原旁白、图片与计划重试并完成。
4. **提交审核之后不再刷新状态。** 为 `submitted` 增加只读核对与退避；平台转码造成文件名和整数秒数变化时，以同账号、作品、标题、创建时间、零编辑及原视频指纹共同确认身份，不能仅凭相近时长放行。
5. **删除成片后可能被当作未制作而重新生产。** 生产完成状态与本地文件可用状态分开；有效释放记录须匹配当前 videoId 和 producerJobId。没有释放凭据的缺文件继续提示处理。
6. **盘点后新增引用可能导致误删；第三份成片漏识别。** 删除前在 SQLite 写锁内重新检查任务输入、回执、保留标记与文件身份，同步删除前不让出执行；第三副本严格匹配任务、工程、Episode、脚本与 SHA。64 项针对性回归和独立复核通过。
7. **渲染缓存检查被持续无关数据库写入阻塞。** 复用未变 JSON 的解析结果，最终引用检查至同步删除由短写锁保护。4 个任务共 1,018 个缓存文件实际移除，3,946,260,711 字节；441 个原素材引用、完整成片和预览均在缓存回收后的检查中保留。已发表成片的后续删除另计。
8. **封面明确限流后自动流程停住。** 原发布意图内按 30/60/120 秒最多追加三次退避恢复，预算跨重启保存；已成功包装复用，有远端任务 ID 或未知结果时不自动重发。899 最终由新逻辑接续成功。
9. **已打开的创作声明弹窗挡住恢复流程。** 原上传 290 的视频和两张封面其实已上传，但恢复时先检查封面，遇到声明窗口即停止。现在先核验原文档、视频指纹、文案及两封面证明，再完成已打开的已知声明窗口。实测沿用原 target 和首次选文件时间，两张封面确认次数仍各为 1，发表请求为 1；没有重传。
10. **平台指纹与列表采用不同的秒数取整。** 284 的本地时长 587.947 秒，原/当前列表均 588 秒，原/当前指纹均 587 秒。改为核验当前指纹与原指纹一致，同时保留账号、作品、创建时间、零编辑、已发表及精确时长容差检查；旧记录无原指纹时继续使用原严格规则。
11. **真实大库下的最终删除锁太长。** 首版并发安全修复在写锁内重复加载全库，实测候选发现约 8 秒，导致三次导出心跳 `SQLITE_BUSY` 异常和后台重启。最终实现缩小发现器的读取范围，锁外解析输入、锁内由 SQLite 比较精确字段与 BLOB 原值，核对行数、rowid、表定义及实时回执；无关心跳不再阻止回收。库存按 250 文件分事务登记，批间至少让步 1 毫秒。心跳首次写入失败也与定时心跳一样上报，不再从轮询同步抛出。实际最后 7 文件已删除且主进程稳定，但首事务仍出现 7.44 秒停顿，不能宣称性能问题全部消除；详见下一节。

## 后续效率优先级

1. 按服务商共享容量控制请求，明确限流时暂停入场并优先续作已有任务；提高本地队列并发无法解除上游 429。
2. 对无复杂动画的镜头评估直接合成通路，保留字幕、音频和镜头合同；复杂地图与动效保留现有渲染器。需要代表产物验证后才能报告加速幅度和质量变化。
3. 分开显示素材等待、画面逐帧、最后合并、上传审核的耗时，防止把整段制作时间误归因于编码。
4. 回收失败显示具体保护原因，并在依赖完成或发表回执更新后再次检查，避免安全保留变成永久积压。
5. 发表核对优先处理刚完成的批次，并复用同账号的作品列表查询。旧待审核记录不应长时间占用唯一核验通道。
6. 失败渲染留下的旧缓存需要独立检查规则；本轮没有把 900 的旧失败目录混入成功缓存批量删除。
